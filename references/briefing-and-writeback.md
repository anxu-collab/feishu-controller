# 汇报、口径对齐、数据计算与受控回写规范

本文件供 `feishu-controller` 在 **Step 1、Step 2、Step 3a、Step 3b** 按需加载。

---

## 1. 结构指纹与口径对齐（Step 1）

### 1.1 结构指纹（`schema_fingerprint`）算法
- 输入：目标表全部分页拉取后的字段元数据列表，仅取每个字段的 `field_id` 与 `type`（整数类型码或规范类型字符串）。
- 排序：按 `field_id` 升序排列。
- 序列化：`json.dumps([[f["field_id"], f["type"]] for f in sorted_fields], separators=(",", ":"))`
- 哈希：`"sha256:" + sha256(utf8_bytes).hexdigest()[:16]`（或完整 64 位，同一实现内保持一致；推荐使用 `scripts/bitable_metrics.py fingerprint`）。
- **严禁把 `field_name` 纳入指纹**：重命名字段不会触发误报漂移。

### 1.2 口径（Lens）对齐与“只问 1 个问题”原则
- 若本地 Ledger 已有同 `(app_token, table_id)` 的最近 `lens_confirmed` 且结构指纹未变（同一 `reader_identity`）：直接沿用，不打扰用户。
- 若首次接入、发生结构漂移、或用户此次请求的指标/维度超出已确认口径：
  - 基于字段列表提出**一个最推荐的默认方案**，把所有需要确认的点收束为**1 个简洁问题**让用户回复确认或微调，例如：
    > “我看到《销售线索》有 12 个字段。默认口径建议：去重键用「线索编号」、时间字段用「创建时间」（时区 Asia/Shanghai）、核心指标统计总数/转化率/各阶段分布。确认按这个口径走，还是需要调整哪一项？”
  - 用户确认后，`lens_version` 设为 `上一版本 + 1`（首次为 `1`），立即追加 `lens_confirmed` 事件。
- 口径尚未确认前，如需先做探索性统计，**去重键强制仅用 `record_id`**，不自行猜测业务主键。

## 2. 在线取数、数据量控制与字段归一化（Step 2）

### 2.1 压低数据量策略（避免撑爆上下文）
1. 优先带上目标 `view_id` 与服务端 `filter`（时间窗、状态筛选），减少无效行传输。
2. 优先使用 `field_names` 投影，只拉取本次口径需要的字段（`record_id` 随结果默认返回，不要放进 `field_names`）。
3. **5,000 行阈值门禁**：
   - 若服务端返回 `total > 5000`，或分页累计达到 5,000 行仍有 `has_more = true`：
   - 立即暂停继续拉取，向用户说明当前表体量，建议通过指定视图、缩小时间范围或加筛选条件把规模压到 5,000 行以内后再汇报。
   - 不要静默截断后假装全量汇报。

### 2.2 飞书特殊字段归一化规则
拉取到的字段值在去重、分组和聚合前，统一按以下规则归一化（`scripts/bitable_metrics.py` 已内置）：

| 飞书字段类型 | 原始常见形态 | 归一化规则 |
|---|---|---|
| 文本 / 富文本 | `"abc"` 或 `[{"text":"a","type":"text"}, ...]` | 拼接 `text` 段落并 `strip()` |
| 数字 / 货币 / 进度 | `12.5` 或 `"12.5"` | 转为浮点数；无法解析记 `None` |
| 单选 | `"进行中"` | 字符串 `strip()` |
| 多选 | `["A", "B"]` | 去空后按字母序排序的列表（用于键时拼为 `"A|B"`） |
| 日期 / 创建时间 / 修改时间 | 毫秒时间戳 `1763942400000` 或 ISO 字符串 | 统一转换为口径时区（默认 `Asia/Shanghai`）的 ISO 日期/时间戳 |
| 复选框 | `true` / `false` | 布尔值 |
| 人员 / 创建人 / 修改人 | `[{"id":"ou_...","name":"张三"}]` 或对象 | 优先取稳定 ID 参与去重，展示时用脱敏/角色或姓名缩写 |
| 超链接 | `{"text":"标题","link":"https://..."}` | 取 `link` 或 `text`（展示用 `text`） |
| 公式 / 查找引用 | `{"type": 1, "value": [...]}` 或嵌套数组 | 解包 `value` 后递归应用上述规则 |
| 附件 | `[{"name":"a.pdf","file_token":"..."}]` | 计附件个数与文件名列表，不拉取二进制内容 |

### 2.3 去重与脚本校验标注
- 按已确认口径的 `dedup_keys` 构建去重键；多条冲突时保留时间字段最新的一条（无时间字段保留最后出现的一条），同时记录 `row_count_raw` 与 `row_count_deduped`。
- 优先把拉取到的记录落到临时文件并运行 `scripts/bitable_metrics.py` 完成确定性计算（运行后及时清理含原始数据的临时文件）。
- 若环境无法运行 Python 脚本，由 Agent 直接计算，但**必须在汇报第 4 段写明：“计算未经脚本校验”**。

## 3. 汇报路径：五项环比门禁与四段式模板（Step 3a）

### 3.1 严格环比准入（五项全一致）
查找同一 `(app_token, table_id)` 最近一条 `briefing_snapshot`，逐项比对：
1. `table_id` 一致
2. `view_id` 一致（同为 `null` 也算一致）
3. `filter_signature` 一致
4. `lens_version` 一致
5. `schema_fingerprint` 一致（且 `reader_identity` 一致）

- **五项全一致**：允许计算环比（增量与变化率），并在第 4 段写明：
  > “环比基线来自本地快照（{上次快照时间}）；若在线历史记录被人修改过，环比差值中会混入这些历史修改，不全是本期真实变化。”
- **任一项不一致（或无历史快照 / 无可读 Ledger）**：不报错、不强行环比，直接标注“环比：不可比（原因：<具体变化项>）”。

### 3.2 四段式汇报模板

```markdown
## 一、核心结论
- 一句话总览（结论先行）
- 关键指标表（本期值 / 上期本地快照基线 / 环比变化 或「不可比（原因）」）

## 二、结构拆解与明细线索
- 按主要维度（状态 / 负责人 / 分类 / 时间段）拆解
- 重点条目列出对应 `record_id` 供用户在飞书定位（默认隐藏手机号、邮箱等 PII）

## 三、异常、风险与待决事项
- 超期项、数据缺失项、去重发现的重复记录（列出 `record_id`）、需要拍板的问题

## 四、口径与可信度声明
- 数据源：`<Base/表名>`（`table_id` / `view_id` / 筛选条件）
- 口径：`lens_version = vN` | 去重键：`[...]` | 时区：`Asia/Shanghai` | 原始行数 X → 去重后 Y
- 校验状态：`已通过脚本确定性校验` 或 **`计算未经脚本校验`**
- 环比声明：`基线为本地快照（YYYY-MM-DD HH:MM）；若在线历史记录被人修改，环比差值会混入该修改` 或 `本次未做环比（不可比原因）`
- 留痕状态：`已追加 briefing_snapshot` 或 **`本次未留痕（无可写存储）`**
```

> 顺序铁律：**先输出完整汇报给用户，再追加 `briefing_snapshot`**，并把本汇报的 `conclusion_summary` 与汇总 `metrics` 写入快照。

## 4. 受控回写路径（Step 3b）

### 4.1 预览与确认（强门禁）
输出回写预览表，至少包含：序号、操作（新增 / 更新）、去重键摘要、将写入的关键字段与值、字段校验提示（如枚举值是否合法）。
- 明确询问用户确认（如“请确认是否执行以上 N 条写入，或指出要修改/取消的行”）。
- **未收到用户明确同意前，严禁调用任何创建/更新接口。**
- 若用户拒绝或取消：不写飞书，直接追加 `bitable_writeback`（`status: "rejected"`、`rejection_reason` 记用户理由），结束流程。

### 4.2 写前幂等查重
用户确认后、真正调用写入前：
1. 取已确认口径的 `dedup_keys`（若无，用该表主字段或用户指定的匹配字段）。
2. 在线检索目标表是否存在同键值记录：
   - **已存在 & 原计划为新增**：默认标记为 `skipped_duplicate`（记录命中 `record_id`）避免重复行；若用户明确授权“存在则覆盖更新”，转为 `update` 并绑定该 `record_id`。
   - 若查重请求本身报错：**停止写入并上报错误**，不要假设“远端不存在”而贸然新建重复行。

### 4.3 分批写入、逐行回执与部分失败重试
1. 按飞书单批上限分批（建议 ≤200 条/批，接口硬上限 500）。
2. 维护逐行回执数组 `rows`，每行记录 `index`、`action`、`status`（`succeeded` / `failed` / `skipped`）、`record_id`、`dedup_hash`、`error`。
3. 若一批中部分行失败（或某批整体失败）：
   - 已成功行锁定其 `record_id`，**绝不重复提交**；
   - 汇总写入结果并展示失败行清单与原因；
   - 用户要求重试时，**只重试 `status == "failed"` 的行**，完成后再记一条新的 `bitable_writeback` 事件。
4. 终态状态判定：
   - 全部成功（含合法跳过重复且 `failed == 0`）→ `status: "confirmed"`
   - 既有成功又有失败 → `status: "partial"`
   - 全部失败（`created + updated == 0 && failed > 0`）→ `status: "failed"`
   - 预览被拒绝 → `status: "rejected"`
5. 拿到完整回执后，追加 `bitable_writeback` 事件到当月 JSONL，并向用户报告最终写入结果与 `record_id`。
